### Complete and Final Project Abstract

**Project Abstract: Code and Documentation Synchronization Management Tool (CodeNexus)**

This project is a desktop application with a highly user-friendly, attractive, and simple graphical interface, designed to bridge the gap between "coding" and "documentation". The primary task of this program is to establish a logical and stable connection between the source code files and the documentation files of a project. The logic of this program is designed entirely without over-engineering, and its features are outlined below:

1. **Resilient and Independent Definition of the Documentation Folder:** At the beginning, the user introduces the path of the documentation folder to the program just once. The program has no sensitivity to the name, size, letter casing, or the depth of nesting of this folder. Importantly, if the user changes the name of this folder in the future, the program will never interpret this name change as a deletion of the folder, and it will preserve all references and settings related to it without any errors.
2. **Deep Scanning and Initial Baseline Creation:** The program scans all code files and folders of the project. This scan is finalized through a mechanism similar to version control systems (such as Add and Commit) to establish a starting point for change tracking.
3. **Real-time and Automatic Change Tracking:** After creating the initial baseline, there is no longer any need for a manual request (clicking a scan button) by the user. The program automatically and in the background detects all changes to code files; including the addition of new files, the deletion of files, and precisely identifying which lines of code in each file have been edited, added, or removed.
4. **Targeted and Many-to-Many Linking:** The user can link code files to related documentation files. The program imposes no limitations in this regard, and a single code file can be simultaneously linked to multiple different documents. By doing so, whenever a user opens a document, they know exactly which code files are connected to it and will exclusively view those for review.
5. **Intelligent Management of Documentation Structure Changes:** If a document is divided into several smaller documents, the user simply links the main document itself to the sub-documents (a document-to-document connection). When the main document is deleted, the program automatically takes all the code files connected to the main document and migrates them to all the sub-documents, without the user needing to manually link each code file individually. After this automatic transfer, the user can optionally remove any redundant files from each sub-document.
6. **Global and Intelligent File Change Alert System:** As soon as the automatic tracking system detects a change (edit or deletion) in a code file, the program identifies **all documents that the file is linked to, without exception**, as requiring an update and places them in the alert list.
7. **Isolated Approval and Commit Cycle (Granular Commit):** The commit (approval) mechanism in this program is never global. After the user updates a specific document, they exclusively approve that same document and the code files directly linked to it. At this exact moment, the new state of *only those files* is recorded, and the alert for *only that document* disappears from the list. Other alerts related to other documents remain completely untouched, so that the user must review and approve each of them individually and separately.
8. **Discovery of Orphaned Code Files (Unlinked Code Files):** The program presents new files detected by the automatic tracking system that have not yet been linked to any document on a dedicated page, allowing the user to connect them to the appropriate documentation.
9. **Filtering and Ignoring (Ignore):** The program features a capability similar to Ignore files to exclude folders or files that do not require documentation from scanning and tracking. This list remains editable at all times.
10. **Lightweight and Portable Storage:** All settings, links, and recorded file states are stored in a hidden folder at the project root (a concept similar to the hidden folder in version control systems). This folder does not contain the actual contents of the files and strictly includes very lightweight metadata so that the project size on GitHub does not become bloated, and all settings are restored upon cloning to another system.
11. **Support for Local Scanning (Sub-folder Scoping):** The user can navigate into a specific folder at any depth within the project and initialize the system for that folder. In this mode, the program operates in a strictly isolated manner; it will have absolutely no access to folders outside that scope and will only manage changes within that specific folder.
12. **Workspace Navigation (Navigation):** In the event that a large project contains multiple folders with independent metadata folders, the program provides a simple navigation system allowing the user to switch between these folders and view only the changes and alerts relevant to the selected folder.
13. **Tracking and Managing Orphaned Documentation (Unlinked Documentation):** The program is capable of identifying documents that exist within the documentation folder but have no code files linked to them. These documents are flagged in the user interface as requiring review, prompting the user to read their content and, upon finding related code in the codebase, link the files to them. If the review reveals that a document is obsolete and useless, the user can delete it directly from within the program, thereby purging both the documentation folder and the program's database of dead documentation.
